## Portal release checks

The advisor and student routes and their read-only API use independent code-level gates. Closed API routes return 503 before verifying a token or accessing Firestore. The portal sign-in uses a school-provisioned Firebase account with a verified email and an in-memory session separate from the staff workspace. The student sign-in uses that private account credential, and a shared URL only opens the sign-in page.

The API derives the lookup key from the verified Firebase identity and reads exactly one `portalViews/{uid}` projection. Each projection binds its UID, role, and active status to the approved account. Student projections carry the stable student ID. Advisor projections carry exact room and course pairs. Rows contain the published assessment title, course label, and scores, with student identity included in the advisor response only. A trusted publishing process must create these projections and remove stale entries when enrollment, advisor assignments, or publication status changes.

Current Firestore rules deny direct reads and writes on this collection. The REST adapter forwards the verified user's Firebase ID token to Firestore, so any future rules that allow this adapter to read a projection also allow the same user to read its raw document. Before enabling the portals, either use a reviewed server-only reader with least-privilege access or prove that every client-readable projection is prefiltered to that account and includes only public-to-that-account fields. The production release also requires a reviewed account provisioning and recovery process, enforced sign-in rate limits, and staging checks for suspensions, revocation, and role boundaries. Use synthetic users for those checks.

## Sakura Student Portal

The Sakura implementation uses `/student` and `/student-admin`. The older `/portal/student` route has its own release policy. The Sakura student and administration pages use independent public gates, `NEXT_PUBLIC_STUDENT_PORTAL_ENABLED` and `NEXT_PUBLIC_STUDENT_PORTAL_ADMIN_ENABLED`. The API additionally requires `STUDENT_PORTAL_SERVER_ENABLED=true`, an explicit `STUDENT_PORTAL_PROJECT_ID`, application default credentials, and the trusted `portalConfig/student.enabled` document. Keep the release gates off until the target project's rules, identities and signing authorization have passed review.

Staff with the `admin` custom claim can manage accounts and course membership. Staff with `admin` or `studentPublisher` can publish or withdraw the result of one student for one term. Share issued passwords privately with their recipient. An account linked before the brokered sign-in flow needs an administrator-issued credential before it can read results. The student signs in with their school number and private password. Published documents contain scoped results, and the reader requires a current student session and reciprocal account binding.

Bulk provisioning validates up to ten explicit student IDs before issuing any credentials, then reports each result independently. A retry skips accounts already created. Use individual recovery if an issued password was lost. Sign-in caps attempts per account and per server counter shard in five-minute windows. Successful sign-in resets the account counter. An exhausted quota can temporarily delay sign-in.

Membership history is entered per student, term and course. A saved window includes coursework assigned at its start and excludes coursework assigned at its end. Leave the final end blank for ongoing membership. An empty saved history excludes that course. When no history has been entered, publication uses the currently active roster as a fallback. Use explicit dates for transfers and historic terms. Withdraw a published term before changing its membership, then publish again. The membership editor detects concurrent changes and records an audit event for each successful save. Updates to source grades require republication to appear in the student view.

### Local verification

Use Node.js 22, Java 21 and the Auth and Firestore emulators for the `demo-gradeflow` project. Bind Auth to `127.0.0.1:9099` and Firestore to `127.0.0.1:8080`. For a local dev server, enable the three portal gates above, set `NEXT_PUBLIC_STUDENT_PORTAL_DEMO_EMULATORS=true`, and point `FIREBASE_AUTH_EMULATOR_HOST`, `FIRESTORE_EMULATOR_HOST` and `STUDENT_PORTAL_PROJECT_ID` at the local emulators and demo project. Use a test-only signing key for custom token issuance and synthetic identities, enrollments and scores. Keep the signing key outside the checkout. Staff auth, Scanner and other workspace components retain their existing configuration.

Check the portal suite with `npm run test:portal`. Run the existing Firestore and recovery suites with `firebase emulators:exec --only firestore --project demo-gradeflow "npm run test:rules && npm run test:recovery"`. Verify provisioning, own-result access, suspension, password recovery, stale-session rejection and withdrawal with synthetic accounts before enabling the portal in any shared environment.
