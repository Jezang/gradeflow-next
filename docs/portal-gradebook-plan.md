## Portal release checks

The advisor and student routes and their read-only API use independent code-level gates. Closed API routes return 503 before verifying a token or accessing Firestore. The portal sign-in uses a school-provisioned Firebase account with a verified email and an in-memory session separate from the staff workspace. The student sign-in uses that private account credential, and a shared URL only opens the sign-in page.

The API derives the lookup key from the verified Firebase identity and reads exactly one `portalViews/{uid}` projection. Each projection binds its UID, role, and active status to the approved account. Student projections carry the stable student ID. Advisor projections carry exact room and course pairs. Rows contain the published assessment title, course label, and scores, with student identity included in the advisor response only. A trusted publishing process must create these projections and remove stale entries when enrollment, advisor assignments, or publication status changes.

Current Firestore rules deny direct reads and writes on this collection. The REST adapter forwards the verified user's Firebase ID token to Firestore, so any future rules that allow this adapter to read a projection also allow the same user to read its raw document. Before enabling the portals, either use a reviewed server-only reader with least-privilege access or prove that every client-readable projection is prefiltered to that account and includes only public-to-that-account fields. The production release also requires a reviewed account provisioning and recovery process, enforced sign-in rate limits, and staging checks for suspensions, revocation, and role boundaries. Use synthetic users for those checks.
